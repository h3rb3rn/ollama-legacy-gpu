The user authorized an inference test on the production instance
`ollama:11436` and then explicitly limited the M10 context to
190000 tokens. Container, image and server configuration were not changed.

- Container `ollama-tesla-bonsai`, image `ollama-bonsai:prod-validated-20260928`.
- Ollama API v0.34.1, CUDA 12 build for sm50/sm52, four Tesla M10 at 8 GiB each.
- Flash Attention off, F16 KV. This differs from the RTX CUDA 13 build
  with Flash Attention and Q4_0 KV; not an isolated hardware comparison.
- Bonsai `27b-pq2_0`, same number-list prompt as in the RTX test,
  temperature 0, seed 42, batch 128, 128 generated tokens each.
- `num_ctx=190000`, internally rounded to 190208.

## Quantized KV cache on Maxwell

The pinned Prism code accepts Q8_0 and Q4_0 for Flash Attention and
contains vector/tile paths for devices without tensor cores. For Bonsai's
head dimension of 256, corresponding quantized kernel instances exist.
There is therefore no fundamental tensor-core prerequisite that would exclude
M10/M60. Q8_0 has since been demonstrated in the subsequent four-GPU test;
Q4_0 has also passed the complete test since.

In the previous CUDA 12 Bonsai build `GGML_CUDA_FA=OFF`. Merely setting
`OLLAMA_KV_CACHE_TYPE` does not add missing CUDA kernels. The prerequisite
for the Ollama route is a CUDA 12 build with Flash Attention followed by
verification of the actual CUDA execution and of the result quality.

Memory requirement for K and V only at 190208 context slots:

| Cache type | Total over four GPUs | Status |
|---|---:|---|
| F16 | 11.61 GiB | measured: 11888 MiB |
| Q8_0 | 6.17 GiB | measured: 6315.50 MiB |
| Q4_0 | 3.27 GiB | measured: 3343.50 MiB |

Calculation: Q8_0 stores 32 values in 34 bytes, Q4_0 in 18 bytes; F16 needs
64 bytes for that. Model weights, recurrent states and compute buffers are not
included in this table. Q8_0 is the first candidate to validate
because of its lower quantization error compared to Q4_0.

The earlier Maxwell FA results in `PERFORMANCE-OPTIMIZATION-LOG.md`
document single-GPU runs with other models. Failures of large multi-GPU MoE
pools documented there prove neither success nor failure of this
Bonsai configuration. The production image was not replaced for this
investigation.

Image `ollama-bonsai:maxwell-fa-20260930`, configuration ID
`sha256:c5ae3f17cfd9bc116dacc141bb5562bc92732aaf190e0ab3d3968a60f5aa24ab`.
Ollama stays at v0.34.1, Prism stays at `adfffbe`, CUDA stays at 12.0.1
with sm50/sm52. The decisive build difference is `GGML_CUDA_FA=ON`.
The candidate uses the same four M10 GPUs and the same model pool
as the production instance, with a separate local test port.

At 190000 requested / 190208 effective context slots:

- Q8_0 for K and V in the actual runner invocation and in the KV cache log.
- Flash Attention active; CUDA capability probe for F16/Q8_0/Q4_0 passed.

- 1578.88 MiB KV per GPU, 6315.50 MiB / 6.17 GiB in total.
- Compute buffer about 962–972 MiB per GPU, compared to 2339–2362 MiB before.

## Q4_0 and ordinary GGUF models: also passed

On the same four M10 GPUs, Q4_0 at 190208 context slots occupies a total of
3343.50 MiB of KV, i.e. 3.27 GiB or 835.88 MiB per GPU. Compared to F16
that is 71.875 % less KV memory. All 65 layers are on the GPU, both
arithmetic answers are correct, and the log contains no CUDA errors.

The two number-list runs measure **1.8314 / 1.8328 tokens/s**, the longer
output with 2048 tokens **1.7903 tokens/s**. Q4 is thus marginally
slower than Q8 here; the additional memory saving does not turn into
an additional speed gain. Two simple correct arithmetic answers
do not prove comprehensive quality equality between Q4, Q8 and F16.

As a separate ordinary GGUF model, `qwen3.5:4b` at 4096 context passed
both cache formats with 34/34 GPU layers, correct arithmetic answers and
2048 stably generated tokens each (about 5.50 tokens/s). All four test runs
returned `passed=true`; the overall test program ended with status 0.
The temporary containers were removed. The protected production containers
kept their IDs, start times and restart counters. In particular,
`ollama-tesla-bonsai` stayed on the previous image, healthy and with restart counter 0.
